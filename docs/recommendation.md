# 関連する求人・おすすめ（閲覧の記録）

求職者の閲覧を記録し、それを使って「関連する求人」と「あなたへのおすすめ」を出す。**機械学習は使わない**（ルールと統計だけ。なぜその順になったかを、数で説明できる）。コードは `backend/events.go`（API・順位づけ・埋め込みの差し込み口 `setEmbedding`）、表は `0006_recruit_events.sql`。

## 契約（API）

| API | 認証 | 内容 |
|---|---|---|
| `POST /api/recruits/{id}/view` | 求職者の Bearer（`/api/auth/me` と同じ。`sub` から利用者が決まる） | 閲覧を記録する。成功は 204（本文なし）。無いトークンは 401。存在しない・表示中でない求人は 404。**同じ利用者・同じ求人は、直近 30 分に 1 件あれば足さない**（それでも 204） |
| `GET /api/recruits/{id}/related?limit=4` | 不要（公開） | `RecruitSummary` の配列（一覧と同じ形。`hero_image` 込み）。自分は含めない・表示中の求人だけ。存在しない（表示中でない）求人は 404。`limit` は 1〜12 |
| `GET /api/recommendations?limit=6` | 求職者の Bearer（401） | `RecruitSummary` の配列。その人がまだ見ていない・表示中の求人から選ぶ。履歴が無ければ `[]`。`limit` は 1〜12 |

## 順位のつけ方

- **共起** = ある 2 つの求人を、どちらも見た利用者の数（人数で数える。同じ人が何回見ても 1）。
- **条件の一致** = 雇用形態・エリア・職種の、共通する項目の数（駅は数えない。マスタの名前は種類の中で重ならないので、コードの一致は名前の一致と同じ）。
- **関連する求人**: (1) 共起の多い順 → (2) 条件の一致の多い順 → (3) ID の昇順。共起が条件より優先される。共起も一致も 0 の求人も、表示中なら後ろに入る。
- **おすすめ**: 得点 = 見た求人との**共起の合計 × 3** + 見た求人との**条件の一致の合計**。見た求人が複数あれば、求人ごとに数えて足す。得点 0 は出さない。同点は ID の昇順。見た求人があとで非表示になっても、その人の「見た求人」には数える（おすすめに出るのは、表示中の求人だけ）。

## 埋め込み（意味の近さ）の差し込み口

- 表 `recruit_embeddings`（求人 ID・モデル名・`double precision[]` のベクトル）と、値を入れる関数 `setEmbedding(ctx, tx, recruitID, model, vector)`（upsert。`events.go`）だけを用意してある。pgvector は使わない（拡張を足さない）。**これを呼ぶ CLI・API は無い。**
- **埋め込みは未投入。** 投入には実 API（求人の文章の埋め込み）が要る。回数・費用を示して承認を得てから行う（ルートの `CLAUDE.md`「実 API・課金」）。このコードベースには、その API を呼ぶ部分が無い。
- 入れると、**両方にベクトルがあるときだけ**、コサイン類似度（0〜1）× 5 を得点に足す。関連する求人では「条件の一致」に足す（共起の優先は変わらない）。おすすめでは、見た求人ごとの類似度の合計を足す。ベクトルが無い・次元が違う・モデルが違う・反対向き（負）は 0。**ベクトルが空のあいだは、上の順位のまま変わらない。**
- 類似度の計算は、その時点の候補をアプリ（Go）で行う。求人が数千件以上になったら、候補を絞る処理（共起・条件で上位だけ）を先に入れる。

## 限界

- **データが少ないと、共起はほとんど 0** で、実質は条件の一致の順になる。ダミーデータで閲覧が少ない間は、この動きになる。
- **共起は利用者の数ベース。** 閲覧した利用者が少ないと、1 人の行動で順位が大きく動く。閲覧の時間・順序・応募は見ていない。閲覧は、記録された回数ではなく、人数で効く。
- **機械学習はしない。** 文章の意味・好み・時期は、埋め込みを入れるまで見ていない。
- **差し替え口は 1 か所。** 順位づけの SQL と得点の式は `events.go` の `rankRelated` / `rankRecommendations`（求人の ID を並べて返すだけ）。中身（埋め込み・学習）を入れ替えても、API の形は変わらない。得点の重み（共起 3・類似度 5）は、同じファイルの定数。
- 全件の候補をその場で計算する（キャッシュ・事前計算なし）。規模が大きくなったら、別の設計にする。

## 個人情報

**どの利用者がどの求人を見たかを、DB（`recruit_events`）に保存する。** 利用者の削除で、その人の記録は消える（`ON DELETE CASCADE`。求人を消したときも、その求人の記録が消える）。記録は、関連・おすすめの計算にだけ使い、他の API には出さない。保存期間の上限・個人が自分の履歴を消す画面は、まだ無い。
